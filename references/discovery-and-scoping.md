# 需求发现与范围界定

适用时机：客户只有一句诉求、零散聊天或会议记录，需要形成可讨论的场景、范围和下一轮确认事项时。选型转到 [solution-selection.md](solution-selection.md)，对外交付结构见 [deliverable-templates.md](deliverable-templates.md)。

## 从碎片材料恢复需求

1. 按材料日期、发言人及其职责整理原始表述，保留可定位的出处；把业务问题、客户指定的解决方式和约束分开。
2. 先复原“谁在什么情况下，当前怎样完成任务，哪里失败或耗时”，再写目标。客户说“做一个智能体”只说明意向，尚不能推出要自动执行业务。
3. 按下表提取已有信息。空缺进入待确认清单，不凭行业常识补成事实；相互矛盾的口径并列记录，找到有决定权的人确认。
4. 把宽泛目标拆成一至数个可验证场景，先写已有证据足够支持的部分。明确哪些缺口阻塞下一步，哪些可暂用可撤销假设推进设计。

| 提取维度 | 需要得到的信息 |
| --- | --- |
| 业务目标、效果目标 | 要改善的业务结果、当前基线、目标指标及计算口径；区分业务收益和技术指标 |
| 目标用户、相关方 | 使用者、受影响者、需求负责人、数据与系统负责人、验收决策者 |
| 核心场景、当前流程 | 触发频率、业务量、现有步骤、人工判断点、痛点及当前兜底方式 |
| 输入、处理、输出 | 输入内容与渠道；查证、判断或执行的动作；结果接收人、格式和使用方式 |
| 数据来源 | 文档或数据库归属、更新频率、可用样本、可信版本、可访问范围 |
| 系统依赖、API/工具 | 涉及哪些系统，现有接口是否可用，读或写、测试环境及维护人 |
| 身份与权限 | 如何识别用户、租户与角色；能查看哪些数据、能执行哪些动作 |
| 隐私与合规 | 敏感数据类别、使用与留存限制、审批责任人及需客户判断的事项 |
| 截止时间、约束 | 业务节点、人员预算、采购或安全审批、不可变限制及可协商项 |
| 排除项、验收标准 | 本期明确不做什么；每个场景的样本、指标、通过条件及签认人 |

## 证据登记与问题排序

按入口规定的四种状态登记；这里补充转化条件，具体记录结构见模板文件。

| 状态 | 判定与下一步 |
| --- | --- |
| 已确认 | 有客户明确答复或有效权威材料；记录来源、日期和适用范围，过期或冲突后重新确认 |
| 推断 | 由上下文推得的工作假设；记录理由、若错误的影响、验证人和最晚确认时间 |
| 建议 | FDE 提出的做法或选项；说明目的、取舍及待客户决定的部分，获采纳后记录决定 |
| 待确认 | 事实缺失、口径冲突或授权不清；写出具体问题、责任人及阻塞的决定 |

提问按影响排序：先处理会改变架构、范围、依赖、安全或验收的事实。例如，“只回答订单问题还是要修改订单”“接口是否支持当前用户范围内查询”“成功以回答正确还是业务动作完成计”。选择本轮最关键的少量问题，说明每个答案将决定什么；其余留在内部清单，不把完整问卷一次推给客户。已有材料能够回答的问题只复述请确认，避免重复访谈。

## 将目标改写成场景

场景句式：“当【触发】发生，【参与者】提供【必要信息】，系统在【授权范围】内执行【动作】，返回【结果】；若【异常】出现，则【兜底或人工交接】。”这是一种需求表达方式，不代表平台已支持对应操作。

例如，内部建议场景可以是：“售后坐席收到退款进度咨询时，提供经授权的订单标识；助手查询进度并给出有来源的解释。标识缺失先补问，权限不足不返回订单内容，查询失败转交售后人员并附查询编号。”该场景仍需确认接口、身份校验和转交渠道，不能直接列成客户已同意范围。

逐场景检查：触发是否可识别、参与者是否唯一清楚、必要信息是否可获得、动作是读还是写、结果能否验收、异常能否终止、接手人是否存在。用主流程和最重要的异常流程限定首期范围，避免用“覆盖全部咨询”替代场景定义。

## 范围与变更测试

范围基线至少包含场景、用户、渠道、数据、系统、允许动作、交付物、排除项和验收口径，并记录版本及确认人。假设日志记录：假设编号、内容、证据状态、依据、错误后果、验证责任人、确认期限、当前结论；高影响假设未关闭时，依赖它的方案只能保持条件成立时有效。

新增诉求出现时依次判断：

- 是否新增用户、渠道、数据域、系统或业务动作？若是，重新评估权限和依赖。
- 是否增加分支、例外、审批或自主执行程度？若是，检查架构与人工接手边界。
- 是否改变数据质量、性能、成本、SLA、截止时间或验收标准？若是，列出资源与验证影响。
- 是否只补充既定场景内的表述或样例？若是，可作为澄清，但仍记录版本和是否影响回归。

输出“原范围—变更内容—影响—可选处理—决定人”。未经范围负责人确认，不把新增要求吸收为原承诺；可先完成不受变更影响的分析。

## 客户会议工作法

会前：汇总已有事实与冲突，准备两三个能检验主路径的真实脱敏案例，列出本次必须决定的问题和需要出席的业务、数据、系统负责人。

会中：按场景走读现有流程，记录原话与出处，区分意见和决定；遇到“应该可以”追问证据或责任人。现场明确接口、样本、审批等行动项的负责人和时间，不代替缺席方承诺。

会后：形成需求理解摘要、范围与排除项、决定记录、待确认事项及行动项。内部保留推断与依据；对客户将未决事项写成请确认的问题或带条件的建议。需要发送时按入口的动作边界处理。

## 常见误区与速查

常见误区：把客户提出的技术名词当成业务目标；把未提到的权限当成无限权限；缺少基线却承诺效果；记录“双方配合”却没有责任人；只定义成功回复，没有异常与人工接手；默认沉默等于同意。

离开本阶段前快速核对：目标与用户清楚；至少一个场景包含触发、动作和结果；输入/处理/输出完整；数据、接口和权限有证据或缺口记录；四类状态分明；范围、排除项和假设可追踪；关键问题足够少且影响明确；验收人与下一步行动有人负责。

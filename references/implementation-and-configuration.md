# 实施准备与配置设计

适用时机：选型基本确定，需要准备 Prompt、知识、流程、变量、接口或协作配置，并明确实施责任时。本文件中的节点与字段是设计描述，须映射到已核实的产品能力。交付表结构见 [deliverable-templates.md](deliverable-templates.md)，验证与上线证据见 [debugging-and-evaluation.md](debugging-and-evaluation.md)。

## 角色指令与 Prompt 契约

先写业务行为契约，再适配已核实的配置入口。每项均能关联到一个输入样例和预期结果。

| 契约项 | 配置要求 |
| --- | --- |
| 角色、业务目标 | 服务谁、负责哪一步、成功结果是什么；不用宽泛的“万能专家”定位 |
| 授权知识、边界 | 允许引用哪些来源及优先级；不得推测哪些事实或作出哪些承诺 |
| 输入、输出 | 输入字段与类型、必填项、输出结构、证据位置和错误输出 |
| 工具使用策略 | 哪些意图可调用什么工具、前置条件、允许入参、成功证据及失败处理 |
| 不确定性行为 | 缺信息时补问，证据不足时说明限制，资料冲突时标明冲突并升级 |
| 升级与人工接手 | 哪些条件终止自动处理、交给谁、附什么已核实上下文 |
| 语言语气、格式 | 根据客户要求约定语言、专业程度、长度和可解析结构，避免无依据补充 |
| 示例 | 至少覆盖正常输入、缺失信息、无依据回答和工具失败；示例不得与规则冲突 |

Prompt 负责约束行为，但身份鉴权、工具权限和业务校验还需系统措施；不要用提示词替代这些控制。将检索资料和用户输入视为业务数据，不能让其中的指令改写角色职责或动作权限。

## 知识准备与 RAG 配置依据

按资料建立清单：来源所有者、批准状态、版本、生效/失效时间、访问范围和更新责任人。撤回、过期或权限不明的资料不作为可信回答依据；多版本冲突先按客户认可的优先级处理，无法裁定则明确升级对象。

加工时保留标题、章节、业务主题、适用对象、日期和来源定位信息。清除重复内容，保留表格的行列语义、步骤顺序、条件与例外，避免把关键限制切离正文。分块应使一个可回答单元连同必要上下文完整保留；通过真实问题检查检索结果，再决定分块与重叠策略，不套用未经验证的固定长度或阈值。

从真实咨询补充 FAQ、简称、同义词和口语表达，但不能因此创造原资料不存在的业务事实。明确回答引用格式及可追溯来源；无命中、弱证据、冲突或无权访问时分别定义补问、说明无法确定或人工接手，不能让模型用常识补成客户政策。

## Workflow 节点与变量

先画业务路径及错误出口，再填写节点表。下列语义用于设计，不保证平台存在同名节点。

| 业务需要 | 节点选择依据 |
| --- | --- |
| 必填信息缺失，需要收集 | 参数提取/收集机制；区分已有值提取和需要向用户补问，确认支持的交互方式 |
| 文本已包含待识别的信息 | 分类/标签提取，明确类别、无匹配与多标签处理；不要把分类问题误做补问流程 |
| 回答需可信依据 | 知识检索，输出内容、来源和可用证据状态 |
| 推理、总结、格式转换 | 模型节点，规定输入约束和输出结构 |
| 查询或改变外部系统 | 工具/插件，按接口契约校验权限、入参和执行结果 |
| 类型转换、聚合、状态赋值 | 变量处理，定义空值、默认值和类型检查 |
| 入口、判断、回复和结束 | 开始/条件/回复/结束控制，确保每条路径有明确出口 |

节点设计表按一行一个节点填写：

| 节点 ID/职责 | 节点类型 | 输入变量/类型/必填 | 输出变量/类型 | 条件 | 工具及前置条件 | 异常处理 | 下一节点 |
| --- | --- | --- | --- | --- | --- | --- | --- |

变量与交接表按一行一个字段填写：

| 名称 | 类型/结构 | 来源 | 消费节点或角色 | 缺值行为 | 敏感性与处理 |
| --- | --- | --- | --- | --- | --- |

区分未提供、空字符串、空集合与查询无结果，不能一概当成“否”。标识符通常应避免数值转换导致前导零丢失；枚举值、时间单位与数组结构在生产者和消费者之间保持一致。敏感字段注明最小传递范围、脱敏和日志限制，不能随共享状态扩散。

## 工具集成就绪条件

每个工具登记以下内容；缺项须说明阻塞哪一步，不能把“接口已提供”视为联调完成。

| 检查组 | 需要的证据 |
| --- | --- |
| 契约与环境 | 接口版本、输入输出结构、字段校验、样例、沙箱/测试端点、与生产环境的差异 |
| 认证与权限 | 凭证取得和轮换责任人、调用身份、最小权限、用户/租户数据边界；凭证值不写入交付物 |
| 幂等与重试 | 是否有幂等键、重复请求识别、超时后结果查询、可重试错误及次数上限；写操作状态不明时先查证，不能盲重试 |
| 超时与错误映射 | 超时预算、业务错误与技术错误、状态码和响应体校验、对用户的解释及人工升级 |
| 回滚与监控 | 可撤销步骤或补偿方案、不可逆边界、请求关联编号、成功/失败/耗时指标和告警接收人 |
| 归属与支持 | 接口业务负责人、维护人、故障联系人、变更通知方式和维护窗口 |

## Multi-Agent 交接契约

仅在方案已说明协作价值时展开：每个角色有唯一主要职责、可用数据和工具范围；每次交接定义输入/输出 schema、证据来源和完成状态。共享状态注明所有者、可写字段、更新规则和版本，避免多个角色互相覆盖结论。

给出明确终止条件（业务完成、预算耗尽、无进展、不可恢复错误）、最大轮次/时长等可验证限制及超限出口。分歧通过证据优先级或指定裁决角色处理，业务决策冲突交给人，不以多次对话自动视为达成一致。交接失败需能追溯发出方、接收方、数据版本和恢复位置。

## 实施顺序与责任

按 mock/stub → 单节点或组件检查 → 端到端测试 → 受控试点/灰度 → 生产推进。每步有输入条件、交付证据和失败退回点；生产前要验证可行的回退方式，不预设平台提供“一键回滚”。

| 工作 | 建议执行方 R | 唯一最终负责方 A | 咨询方 C | 知会方 I |
| --- | --- | --- | --- | --- |
| 业务范围与验收 | 客户业务负责人、FDE | 客户指定项目负责人 | 一线用户、验收人 | 交付团队 |
| 资料整理与授权 | 客户数据负责人 | 客户指定数据责任人 | 安全/合规、FDE | 业务负责人 |
| 配置与联调 | FDE、客户接口维护人 | 指定技术交付负责人 | 平台支持、安全人员 | 项目负责人 |
| 评测与缺陷关闭 | FDE、客户测试人员 | 指定验收负责人 | 业务、接口维护人 | 运维团队 |
| 发布与运行 | 获授权的发布及运维人员 | 指定发布负责人 | FDE、业务、安全人员 | 支持与用户代表 |

以上为建议分工，实施前替换为客户确认的实名或团队，每行 A 唯一。客户前置条件包括：可用脱敏样本、批准的知识资料、测试身份与权限、接口契约和测试环境、业务验收人、试点用户、发布窗口及故障接手人。

读取配置、日志和页面并形成设计可直接推进；将设计转为线上变更或外部副作用时，执行入口规定的动作前确认。为具体动作准备可审阅的环境、对象、拟改值/提交内容、影响、验证方式和恢复方案；“同意方案”不能替代这一动作步骤。

## 常见误区与就绪检查

常见误区：只写 Prompt 不整备知识；用参数补问代替已有文本分类；变量靠同名猜测传递；工具成功仅看 HTTP 状态；把超时当成未执行；多角色没有终止条件；客户前置条件未落实就承诺日期。

就绪检查：Prompt 契约可验证；资料有版本与权限；节点有正常/异常出口；变量有类型、缺值和敏感处理；接口契约与幂等明确；适用时交接可终止；RACI 有负责人；测试环境及客户前置条件齐全；每步有验证和回退；实际操作确认材料已准备。

# 调试、评测与上线证据

适用时机：已有异常输出、Badcase、配置修改，或需要评测、试点和验收证据时。配置设计细节见 [implementation-and-configuration.md](implementation-and-configuration.md)，记录结构见 [deliverable-templates.md](deliverable-templates.md)。

## 验证节奏与单例闭环

依次进行：构建期单例调试 → 针对薄弱环节专项验证 → 主路径稳定后的批量评测 → 每次变更后的回归。尚不能稳定复现和解释主路径时，先修正链路，再用批量结果衡量质量；规模化评测不能替代定位。

单例五步法：

1. 定目标：写明该输入应经过的分支、依赖证据、预期动作和输出。
2. 选输入：使用可解释、可复现的脱敏输入，固定配置、知识和接口环境版本。
3. 查全链：串联意图、检索、Prompt、变量、节点、工具、输出与兜底记录，定位最早偏离预期的位置。
4. 记主改动：提出可证伪的根因假设，一次只记录并实施一个主要调整，保留修改前证据。
5. 复测扩展：重跑原例及相邻类别、边界和旧 Badcase；结果改善后仍要检查是否引入副作用。

“模型没理解”不是根因。可用于记录的根因应能定位、解释并验证，例如“订单标识被转成数字后丢失前导零，工具查询了错误标识”。链路证据不足时记录候选原因及所需证据，不能直接判定要换模型或改 Prompt。

## 按依赖顺序定位

| 顺序与层级 | 检查内容与可用证据 |
| --- | --- |
| 1 意图/分支 | 用户实际目标、分类结果、分支条件与执行轨迹是否一致；先看上游是否选错路径 |
| 2 知识/RAG | 目标知识是否存在、有权访问且有效；查询表达、切分上下文、检索返回、阈值或过滤是否丢失证据；具体可调项先核实 |
| 3 Prompt | 实际收到的指令与证据是否完整、冲突；是否要求按来源回答，输出格式是否明确，示例是否误导 |
| 4 变量 | 提取结果、字段映射、来源/消费关系、类型、空值与覆盖顺序；对照节点实际输入输出 |
| 5 节点 | 选型、连接、条件计算和正常/异常出口是否符合业务；不要用补问信息的机制替代已有文本分类 |
| 6 工具 | 入参、身份/权限、状态、响应体及业务结果、重复请求/幂等；超时后是否已经执行 |
| 7 最终输出 | 是否正确引用证据、完整回答、符合语言与结构，是否虚报未完成动作 |
| 8 异常兜底 | 无知识、无权限、缺字段或工具失败时能否结束、解释并交给明确接手方 |
| 9 延迟 | 分段耗时、排队、检索、模型、工具和重试耗时，定位慢点而非只看总时长 |
| 10 成本 | 调用次数、上下文长度、token、重复检索与循环；以实际计量和业务量估算 |

并非每个案例都需修改每层；对不存在的层记录“不适用”及原因，不可跳过尚未检查的 RAG 等环节并声称完整诊断。

Workflow 专项检查：主路和每个条件分支均有可到达测试；变量类型在节点间一致；缺值和无匹配分支可退出；工具错误不会走成功回复；重试有上限，重复进入不会重复提交；人工批准点位于真实动作之前。

Multi-Agent 专项检查：角色职责是否重叠或遗漏；交接字段、证据、版本是否完整；接收方是否正确消费；冲突裁决和共享状态更新是否确定；无进展、循环交接和预算超限能否终止；最终答复责任及人工升级是否明确。协作收益用同一评测集与简单方案比较。

## Badcase 与测试集

每个 Badcase 必须有七个字段：问题/输入、期望结果、实际结果、失败层级/根因、修改动作、复测结果、回归案例。版本和负责人可获得时一并记录；未复测只能标记待验证，不能标为已修复。根因包含证据，变更包含具体差异，复测包含可定位结果。

### Badcase 输出合同

对单个 Badcase，先按以下顺序交付诊断记录，再给出任何配置建议或实施步骤。这个结构使事实、判断、平台能力和待验证改动可分别复核：

1. **已观察到的执行证据**：记录可定位的输入、版本/环境、实际分支或调用轨迹、节点输入输出、检索或工具记录、最终回复和时间/计量；证据不足时明确缺少哪一条记录。
2. **根因假设**：基于上述证据说明最早偏离预期的位置、候选原因及其可证伪方式。尚未证实的原因保留为假设，不把“模型没理解”作为结论。
3. **控制可用性与证据**：逐项记录拟用控制在当前客户环境中的已检查结果，或当前腾讯云官方资料的证据。意图优先级、排除词、置信度阈值、澄清出口、改写/输出检查节点，以及任何 UI 或配置项，都属于需要本步证据的产品控制。
4. **拟议改动**：仅在控制已由第 3 步证实时，将其写为可执行配置改动并说明作用层、具体差异、依赖与可回退点。每项改动附一项 **控制面映射**：控制名称、实际拥有该控制的组件/节点类型、该客户当前配置的检查证据或当前官方资料证据（含可定位来源）、以及实施位置。按这份映射在真实拥有控制的组件中配置；不得把某一节点类型的已记录控制转述为另一节点类型的能力。若尚未检查客户环境和当前官方证据，所有变更只能放在 `待确认后的条件性修复草案`，不得使用“立即调整”“直接修改”“已核验节点”或其他暗示控制已经存在的表述。每项草案写成带 `待平台确认` 的条件能力需求，例如“若核验存在可配置的意图优先级，则……”；同时给出不依赖该控件名称的概念级替代路径，例如以已存在的明确业务边界、正反例、缺失信息澄清或人工接手来收敛风险，直到能力得到确认。仅有症状、没有客户配置或当前官方证据时，能力核验仍未通过；条件措辞本身不是能力证据。

语言输出的控制面映射示例：先确认实际参与生成的模型节点及其指令面；将语言指令放入已核验的模型生成节点。回复/展示节点则使用中文模板或已验证来自上游的中文文本；只有当前配置或官方证据证明该节点另有语言控制时，才在该节点声明和使用该能力。实际回复路径或控件归属未知时，标记 `待平台确认`，并以已验证的中文模板或人工接手作为临时呈现路径。
5. **修复结构选择**：使用可见的小节名称 `修复结构选择`，写明选定的最小修复结构及其组成，并逐一说明该结构如何隔离第 1 步已观察到的失败层级。接着说明为何无需更广的 Workflow、Multi-Agent 或 Claw 重设计；理由须对应当前链路中不存在的分支编排、跨角色交接/共享状态或自主外部动作。若认为需要更广设计，则列出会触发该判断的执行证据、待验证的结构能力和比较方式，而不是以产品名称代替理由。
6. **验证与回归**：为原 Badcase、相邻表达、边界输入和历史回归例写明预期轨迹、可观察证据、通过标准、版本和结果记录位置。未运行的项标记待验证。

每份 Badcase 诊断均须覆盖下列八个层级；每格填入已观察到的执行证据，或填入有依据的 `不适用`（说明检查对象为何不存在或不参与该链路）。这是一份诊断记录，不是待办清单：仅写“路由至知识库”或“检查知识库”不构成 RAG/检索诊断。

| 诊断层级 | 必须记录的证据或有依据的 `不适用` |
| --- | --- |
| 意图/分支 | 用户目标、分类/条件结果、实际进入分支与预期的差异 |
| RAG/检索 | 知识是否参与该执行链路；参与时记录授权版本、查询、过滤/访问条件、返回片段与注入上下文；未参与时说明对应分支或调用轨迹依据 |
| Prompt | 实际生效的指令、示例和输入证据是否完整或冲突 |
| 变量 | 提取值、字段映射、类型、空值、覆盖顺序及节点间流向 |
| 节点 | 已执行节点、连接/条件计算、正常与异常出口 |
| 工具 | 入参、身份/权限、响应和业务状态；未调用也要由轨迹佐证 |
| 输出/兜底 | 最终文本、所用证据、语言/结构，以及无知识、缺参或失败时的实际出口 |
| 延迟/成本 | 分段耗时、调用次数、上下文或 token 等实际计量；未采集时记录缺失并将结论限定为待测，而非凭总时长推断 |

第 5 步的 `修复结构选择` 是每份 Badcase 的可见必填小节，而非仅附在建议末尾的说明。该选择以实际链路复杂度为依据，不以产品名称替代架构理由。

| 测试类别 | 应覆盖的挑战 |
| --- | --- |
| 标准问题 | 高频主路径、典型知识与成功工具调用 |
| 口语/同义表达 | 简称、错别字、不同措辞下意图与证据仍一致 |
| 信息缺失 | 必填字段缺失、含糊、多轮补充、空值或格式错误 |
| 边界/安全 | 无权访问、越界操作、敏感信息、指令注入、无依据承诺和人工审批 |
| 复杂组合 | 多意图、跨知识与工具、多条件、冲突资料和上下文切换 |
| 工具失败 | 拒绝认证、限流、超时、无结果、异常响应、重复请求与执行状态不明 |
| 回归 | 历史 Badcase、相邻场景、关键分支和高影响动作 |

评测行需有唯一编号、类别、输入、前提/版本、预期证据或动作、判定标准、实际结果和评分。开发调试样本与验收保留样本区分使用；验收样本和口径先与客户对齐，避免只挑通过案例。

## 指标菜单与结果解读

按场景挑选必要指标并固定分母、评分方式和失败定义，不强制全部使用。

| 指标 | 口径要点 |
| --- | --- |
| 回答正确性/有据性 | 分开评估业务答案正确与是否由授权证据支持，保留人工判定依据 |
| 检索命中/召回 | 命中指是否找到预期证据；召回需要已标注的相关证据集合，不能用回答准确率代替 |
| 任务完成率、必填完整率 | 是否达到业务终态；必填字段的有效性与完整性分别明确 |
| 工具成功率 | 同时满足技术返回与业务完成标准；重试与重复调用的分母单独约定 |
| 人工接手率 | 区分设计要求的正常转交和自动处理失败，不能一味压低 |
| 延迟、token/成本 | 按请求统计并注明样本量、分布或分位数；费用用有效计价和实际用量核算 |
| 满意度 | 说明评价人、量表、样本及缺失评价的处理，不与自动评分混用 |
| 关键安全失败 | 单独列出越权、泄露、未经批准的动作等事件，不让平均分掩盖高影响失败 |

分场景报告样本数、通过/失败/未测、不适用项、关键失败和已知限制；不能用很小或偏置的样本外推全量业务表现。

## 上线门槛与验收

门槛必须按场景与失败影响商定，不能套用无依据的统一百分比。至少明确验收样本和版本、所选指标目标、关键分支与异常覆盖、未解决关键 Badcase、回退路径、监控项/告警、运行与接手负责人。

仍有未解决关键 Badcase，或动作权限、回退、监控、责任不清时，不给出可直接生产上线的建议。先修复和复测，或将受影响场景明确排除并重新确认试点范围及验收边界。任何例外需留下有权限者的决定、残余风险和限制，不能写成默认通过。

上线判断应附评测证据、试点范围、停止条件和恢复演练结果；操作本身遵循入口边界。变更知识、Prompt、节点、工具或模型后，回归直接受影响场景以及关键安全路径。验收按“已达成/部分达成/未达成/不在范围内”记录，每项都关联范围基线与证据，区分接受残余风险和已解决问题。

## 常见误区与症状速查

常见误区：只调 Prompt；一次改多个层却无法归因；工具返回 200 就宣称成功；用平均分掩盖越权；只测原 Badcase；把“可以回滚”当成已验证恢复能力；以客户催促替代上线证据。

| 症状 | 首查层级 | 下一步证据 |
| --- | --- | --- |
| 进入错误业务路径 | 意图/分支 | 实际分类及条件计算结果 |
| 文档有答案却答错 | 知识/RAG | 有效版本、访问过滤、返回片段及上下文 |
| 内容正确但格式/语言错误 | Prompt、最终输出 | 实际指令、样例与输出约束 |
| 总在补问已有信息 | 变量、节点选择 | 已提取字段、类型和补问条件 |
| 查询失败或操作重复 | 工具 | 入参、身份、业务状态、幂等与重试记录 |
| 多角色反复互相转交 | 交接、终止控制 | 交接轨迹、状态变化及预算计数 |
| 响应越来越慢或成本上升 | 分段延迟、调用量 | 耗时、token、循环和重试分布 |

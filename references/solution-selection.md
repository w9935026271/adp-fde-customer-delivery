# 方案选型与架构取舍

适用时机：业务场景已有轮廓，需要选择 ADP 方案路径、解释架构或评审复杂度时。场景缺口回到 [discovery-and-scoping.md](discovery-and-scoping.md)，确定方案后进入 [implementation-and-configuration.md](implementation-and-configuration.md)。

## 先看任务结构，再选择模式

先判定任务是否确定、步骤及分支数量、工具/API 调用方式、角色专长是否必要、自主程度、可追踪要求、失败影响和人工批准点。模式名称只是设计候选；是否在客户当前环境可用按入口的官方核验规则处理。

| 候选方式 | 适用条件与推荐理由 | 不宜使用或需补证的情况 | 关键控制点 |
| --- | --- | --- | --- |
| 标准模式 | 默认用于边界明确的对话、知识问答、少量上下文处理；步骤简单且不需要显式流程控制 | 需要稳定执行多步骤业务、复杂分支或严格逐步审计时需重新评估 | 限定知识与动作边界，回答证据、补问和人工转交可验收 |
| Workflow | 步骤、先后关系和条件可定义；需显式编排查询、判断、批准与执行 | 只有简单问答，或业务规则尚未明确时，新增流程未必有价值 | 节点输入输出、分支覆盖、错误出口、审批与可追踪性 |
| Multi-Agent | 不同专业角色必须协作，交接比单一角色带来可测收益，如质量、职责隔离或吞吐改善 | 只是把同一 Prompt 切成多个角色，或没有对照证据证明协作收益 | 交接契约、共享状态、冲突裁决、终止与人工升级 |
| Claw | 业务确需自主执行循环：根据反馈继续规划、行动、检查，且该能力与环境支持已核实 | 一次性生成、固定流程或普通问答无需引入；支持情况不明时只能条件设计 | 最小权限、执行预算、动作批准点、停止条件、恢复及审计 |
| 组合 | 场景确有不同任务结构，可明确入口、出口和责任，例如固定流程中调用受限问答组件 | 无法解释每个组件的独立价值，或错误和权限边界相互穿透 | 写清跨组件数据、权限、超时、失败归属与最终输出责任 |

实用判断顺序：有限问答先考虑标准模式；稳定多步及分支考虑 Workflow；只有角色专业化与交接能证明收益才考虑 Multi-Agent；只有反馈驱动的自主循环不可缺少且支持得到核实才考虑 Claw。失败影响越高，越要明确可审计步骤、人工批准与恢复方式，不能据此简单推导某个模式“更安全”。

遵循 YAGNI：不为未来可能出现的复杂性预建 Multi-Agent、Workflow 或 Claw。以相同场景样本比较复杂方案与简单方案；若质量或业务收益不足以抵消延迟、成本、调试和运维负担，保留简单方案。

## 架构覆盖检查

覆盖是逐项作出决定，不是逐项启用。对不需要的组件写明“不采用”和理由；配置方法只放在实施参考中。

| 架构层 | 本阶段应回答的决定 |
| --- | --- |
| 应用与模型 | 用户从何处进入，模型承担何种任务；质量、时延、成本和数据要求如何验证 |
| 角色指令、变量、长期记忆 | 行为契约是什么；哪些是单次输入、会话状态或跨会话记忆；记忆是否必要、谁可读写、如何过期与纠正 |
| 知识库与 RAG | 哪些回答必须基于受控资料，数据更新与访问边界是什么，证据不足如何退出 |
| 工具、连接器、Skills | 工具执行什么动作，连接器连接哪些数据或系统，Skills 复用哪些任务方法；避免职责重叠，确认实际可用性与权限 |
| Workflow | 哪些顺序、条件或批准点需要显式控制；业务状态由谁维护 |
| Multi-Agent | 哪些角色不可合并，谁协调，交接带来的收益如何测量 |
| Claw | 哪些任务需要自主循环，动作范围与停止条件是什么；无法证实支持时不进入实施承诺 |
| 权限与人工接手 | 身份和数据权限在哪里生效，哪类动作需批准，异常交给谁以及交接什么 |
| 可观测性与兜底 | 如何关联请求、检索、节点和工具记录；错误如何被发现、定位、停止或恢复 |

对组合架构写一条完整业务链，标明组件边界。例如“用户请求 → 权限判断 → 知识答复或订单查询路径 → 汇总答复/人工接手”。这是概念架构，不暗示存在同名产品节点或控件。

## 推荐方案与备选方案

输出一个推荐方案，最多一个有实质取舍的备选方案。每个方案都给出：适用场景与理由、依赖、限制、风险和验证要求。对无实际差异的备选不要凑数。

推荐理由要连到客户目标与证据，如“流程存在固定必填项及明确分支，因此建议用可追踪的步骤表达”；不能只说“能力更强”。依赖要标识当前状态与责任人；风险需说明发生条件和业务影响；验证要求应指向一个样本、一次接口检查或一项评测，而不是“进一步验证”。

用一个反例检验推荐方案：若接口不可用、资料未获准使用、跨会话记忆不允许或自主执行不能获批，方案是否仍能交付缩小后的价值？写清降级条件、影响及需重新决定的范围。

## 产品事实核验

涉及当前模型支持、节点名称、连接器、配额、记忆机制、Claw、发布方式或限制时，查看当前腾讯云官方资料，并记录链接、核验日期和适用环境。无法获得证据或资料未覆盖该能力时，将该项标为 `待平台确认`，列出具体待核实问题及验证责任人；官方页面的存在不等于客户账号、地域或版本可用。

教材提供选型方法，不能作为当前产品支持清单。方案可以描述所需能力，但不要把它写成未经验证的 ADP 页面按钮、配置开关或现成接口。

## 常见误区与速查

常见误区：把多步骤等同于必须多智能体；给简单问答叠加自主循环；把不同角色名视为专业协作收益；用模式代替权限设计；只画成功链路；把概念方案当作已验证能力。

| 速查问题 | 通过依据 |
| --- | --- |
| 为什么选这种模式？ | 可关联任务确定性、步骤/分支、工具、角色或自主循环需求 |
| 为什么不能更简单？ | 有具体场景或评测证据，不是抽象的扩展性理由 |
| 架构是否完整？ | 各层采用或不采用有决定，跨组件责任明确 |
| 关键依赖是否可用？ | 有核验记录；未知项标记并限定方案成立条件 |
| 怎样证明可交付？ | 推荐与备选均有局限、风险、样本验证和验收路径 |
